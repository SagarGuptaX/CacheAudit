# CacheAudit

A trace-driven benchmarking framework for studying cache eviction policy behavior.

CacheAudit is not a production caching library.  
Its purpose is to run controlled experiments on access traces, compare eviction policies, and explain the tradeoffs using data.

---

## What it does

- Loads access traces from disk and normalizes string keys to integer IDs once
- Runs a chosen eviction policy over the trace
- Measures hit rate, miss count, and wall-clock runtime
- Exports results to CSV for comparison and plotting

---

## Architecture

```
Trace file (R/W key)
       |
   TraceLoader
       |
    KeyMapper          <- string -> int, assigned once, never again
       |
  vector<Request>      <- integer-only from here down
       |
     Runner
       |
   Cache (abstract)
   /   |   |   |   \
FIFO LRU LFU ARC Belady
       |
    Metrics
       |
  stdout summary + CSV row
```

**Design rule:** string handling ends at the KeyMapper. Every policy operates on integer IDs only. This avoids repeated string hashing in the hot path and keeps the cache layer clean.

## Eviction Policies

| Policy | Core data structures | Eviction rule |
|---|---|---|
| FIFO | deque + unordered_set | Evict the oldest inserted item |
| LRU | std::list + iterator map | Evict the least recently used |
| LFU | std::set (frequency tree) + lookup map | Evict the least frequently used, LRU as tiebreak |
| ARC | Four lists (T1, T2, B1, B2) + adaptive `p` | Self-tuning between recency and frequency |
| Belady | Precomputed next-use map + unordered_set | Evict the item needed furthest in the future |

**FIFO** — simple, predictable, but ignores access patterns. A recently inserted item is protected; a frequently accessed item is not.

**LRU** — recency-based. Handles temporal locality well. Thrashes on sequential scans larger than the cache. O(1) move-to-front via `std::list::splice`.

**LFU** — frequency-based. Protects hot items from cold floods. Uses a `std::set` sorted by `(frequency ASC, last_access ASC)` so `begin()` is always the eviction victim. Update requires remove → modify → reinsert since `std::set` elements are immutable.

**ARC** — adaptive. Maintains ghost lists (B1, B2) of recently evicted items. Ghost hits in B1 signal recency was important; ghost hits in B2 signal frequency was important. Adjusts the balance between T1 (recent) and T2 (frequent) at runtime. No manual tuning required.

**Belady** — offline optimal. Requires the full trace upfront. Preprocesses next-access times and uses binary search (`std::upper_bound`) to find the item with the furthest future use at eviction time. Not usable online; exists to show how far real policies are from optimal.

## Workload Traces

All traces live in `traces/synthetic/`. Generated by `scripts/gen_traces.py`.

### loop
Items 0–29 cycled 20 times. Working set = 30 items.

```
size=10: all online policies thrash (0% hit rate)
size=20: all online policies thrash (0% hit rate)
size=40: cache > working set, all policies ~95%
```

Below the working set threshold, all online policies fail equally. Belady achieves non-zero hit rates even below threshold (30% at size=10, 63% at size=20) by knowing which items will be needed soonest.

### scan
1000 unique items, each accessed exactly once. Hit rate is 0% for all policies by definition.  
Purpose: all-miss baseline. Runtime differences here reflect per-policy overhead, not quality.

### skewed
Item 0 is a hot key pre-warmed with 10 accesses, then revisited at the end of each cycle. Items 1–29 cycle cold.

```
size=10: FIFO/LRU = 1.5%,  LFU/ARC = 4.75%,  Belady = 31%
size=20: FIFO/LRU = 1.5%,  LFU/ARC = 4.75%,  Belady = 64%
```

LFU and ARC protect the hot key because its accumulated frequency outweighs cold items. LRU evicts the hot key during cold floods because it becomes the least recently used candidate.

### hot_cold
5 hot items pre-warmed 15 times each. Then 30 cycles of: 20 **unique** cold items flood through (fresh IDs every cycle, never repeated), followed by all 5 hot items.

```
size=10: FIFO/LRU = 8.5%,  LFU/ARC/Belady = 26.7%
size=20: FIFO/LRU = 8.5%,  LFU/ARC/Belady = 26.7%
size=40: FIFO = 17.6%, LRU/LFU/ARC/Belady = 26.7%
```

26.7% is the ceiling for this trace: warmup hits (70) + cycle-end hot hits (150) / total requests (825).

**Why unique cold items per cycle (critical design decision):** If cold items repeated across cycles, they would build up ghost history in ARC's B1 list. B1 ghost hits trigger a cascade that drives `p` up until it equals `T1.size()`, at which point the `replace()` function switches from evicting T1 to evicting T2 — which contains the hot items. At cap=20, this cascade causes hot items to be continuously cycled through B2 as misses, producing a non-monotone result (larger cache = worse performance). Using unique cold items eliminates this: cold items are never revisited, B1 ghost hits never occur, `p` stays at 0, and T2 remains clean throughout.

**FIFO vs LRU at size=40:** FIFO cannot reorder items on access. Hot items (inserted during warmup) sit at the front of the queue and are evicted periodically as the cache cycles through cold batches. LRU moves hot items to the MRU position on every access, protecting them across cold floods. At size=40, this recency difference becomes visible: FIFO loses some hot-item hits that LRU retains.

## Build

Requires a C++17 compiler and CMake 3.10+.

```bash
cmake -B build
cmake --build build
```

Or directly with g++:

```bash
g++ -std=c++17 -Wall -Wextra -O2 -I src \
    src/main.cpp src/engine/trace_loader.cpp \
    -o cache_audit
```

## Usage

```bash
# Generate traces
python3 scripts/gen_traces.py

# Run one experiment
./cache_audit traces/synthetic/loop.txt lru 40

# Run with CSV output
./cache_audit traces/synthetic/hot_cold.txt arc 10 --out results/out.csv

# Run all 60 experiments (5 policies × 4 traces × 3 sizes)
bash scripts/run_experiments.sh
```

**Policies:** `fifo` `lru` `lfu` `arc` `belady`

## Key design decisions

**Why hash maps everywhere?**  
All policies use hash-based lookups. Real production caches do too — no one ships an O(n) linear scan. If lookup complexity differed across policies, the lookup cost would dominate the timing results and obscure the eviction logic comparison. Using consistent O(1) lookups means timing differences reflect eviction overhead, not lookup overhead.

**Why integer IDs?**  
String hashing on every access would pollute timing results with allocator and hash cost. Normalizing once at load time means the hot path is integer comparison only.

**Why load the full trace into memory?**  
Belady requires future knowledge by definition. Loading everything upfront gives all policies the same execution model and avoids two separate code paths for streaming vs. offline policies.

**Why not a slab allocator?**  
Out of scope for this project. The question being studied is "given reasonable memory management, what are the tradeoffs between eviction policies?" — not "which policy benefits most from custom allocators."

## Project structure

```
src/
  engine/
    request.h          — Request{Op, id} struct
    key_mapper.h       — string -> int normalization
    trace_loader.h/cpp — reads trace file, invokes KeyMapper
    cache.h            — abstract base class, access(int id)
    metrics.h          — Metrics struct (hit_rate, misses, runtime_ms)
    runner.h           — simulation loop + chrono timing
  policies/
    fifo.h
    lru.h
    lfu.h
    arc.h
    belady.h
  main.cpp             — CLI, policy factory, CSV append

scripts/
  gen_traces.py        — generates all synthetic traces
  run_experiments.sh   — batch runner (5 × 4 × 3 = 60 runs)

traces/
  synthetic/           — loop, scan, skewed, hot_cold

results/               — CSV output lives here (gitignored)
```
